In [Chapter 3](/course/chapter3), we looked at how to fine-tune a model on a given task. When we do that, we use the same tokenizer that the model was pretrained with -- but what do we do when we want to train a model from scratch? In these cases, using a tokenizer that was pretrained on a corpus from another domain or language is typically suboptimal. For example, a tokenizer that's trained on an English corpus will perform poorly on a corpus of Japanese texts because the use of spaces and punctuation is very different in the two languages.

In this chapter, you will learn how to train a brand new tokenizer on a corpus of texts, so it can then be used to pretrain a language model. This will all be done with the help of the [🤗 Tokenizers](https://github.com/huggingface/tokenizers) library, which provides the "fast" tokenizers in the [🤗 Transformers](https://github.com/huggingface/transformers) library. We'll take a close look at the features that this library provides, and explore how the fast tokenizers differ from the "slow" versions.

Topics we will cover include:

* How to train a new tokenizer similar to the one used by a given checkpoint on a new corpus of texts
* The special features of fast tokenizers
* The differences between the three main subword tokenization algorithms used in NLP today
* How to build a tokenizer from scratch with the 🤗 Tokenizers library and train it on some data

The techniques introduced in this chapter will prepare you for the section in [Chapter 7](/course/chapter7/6) where we look at creating a language model for Python source code. Let's start by looking at what it means to "train" a tokenizer in the first place.

## Applied Lab: Worked Decision Example for Tokenizer Strategy[[applied-lab-worked-decision-example]]

### Lesson connection

As introduced above, deciding whether to reuse an existing tokenizer or train a new one from scratch depends critically on the target corpus domain and training objective. When pretraining on code or domain-specific language from scratch, using an off-the-shelf English tokenizer is suboptimal because whitespace, indentation, and syntax symbols are segmented poorly. Conversely, fine-tuning on a task in the original language reuses the pretrained tokenizer to preserve embedding weights.

The applied lab below provides a deterministic offline decision engine and verification checker representing these principles.

### Published Decision Table

| `normal_scratch_domain_shift` | **Normal Scenario**: Pretraining from scratch on Python Code | `mode="scratch"`, `domain="python_code"`, `corpus=[sample code]` | `TRAIN_NEW_TOKENIZER` | Recaps Section 1: Pretraining from scratch on a new domain requires training a new tokenizer to avoid suboptimal whitespace and vocabulary segmentation. |
| `boundary_minimal_single_sample` | **Boundary Scenario**: Minimal single-sample corpus | `mode="scratch"`, `corpus=["single text sample"]` | `TRAIN_NEW_TOKENIZER` | Minimal valid input boundary: Exactly one non-empty string sample fulfills the iterator contract for vocabulary training without raising empty-data errors. |
| `missing_information_null_corpus` | **Missing-Information Scenario**: Null corpus iterator | `mode="scratch"`, `corpus=None` | `REJECT_MISSING_CORPUS` | Missing-information failure: Tokenizer training cannot proceed without text data to discover subword merges. | `boundary_matching_domain_fine_tune` | **Boundary Scenario**: Standard fine-tuning on matching domain | `mode="fine_tune"`, `domain="english"`, `pretrained="english"` | `REUSE_PRETRAINED_TOKENIZER` | Recaps Chapter 3 / Chapter 6 contrast: In downstream fine-tuning on the same domain, reusing the checkpoint's tokenizer preserves learned embedding alignments. |
